# Security and privacy

Authenticated APIs require `x-api-key`; only SHA-256 digests of keys are stored. Tenant ID is taken from that digest for every call/document/lead/appointment read. Browser demo access is limited to a configured tenant and chat only. The Twilio webhook checks `X-Twilio-Signature` against the configured public URL and form parameters before creating a call. See [Twilio's signature guidance](https://www.twilio.com/docs/usage/webhooks/webhooks-security). Twilio recommends its SDK validator; the pilot currently implements the form signature algorithm directly, and must be validated against live requests before production.

Secrets are supplied through environment variables and must never be committed. Public browser demo has a process-local IP limiter only. API keys have no expiry/rotation. SQLite files contain transcripts, lead names/phone numbers, and call events in plaintext; protect the volume and restrict access. No automatic deletion, encryption at rest, recording consent workflow, transcript redaction, or data export/deletion API exists. No call recordings are stored. Applicable call recording, notification, marketing, and retention rules vary by jurisdiction and must be reviewed before real use.

Retrieved documents are treated as lower-trust context, with a policy instruction and explicit known injection phrases, but there is no reliable prompt-injection guarantee. Do not upload sensitive or untrusted documents without human review. Provider access tokens are process-wide but bound to exactly one tenant ID by configuration. For multi-tenant production, use a proper tenant-scoped secret manager, OAuth refresh, audit controls, and RBAC. Rate limits and replay locks must move to a shared durable service before multiple replicas run.
