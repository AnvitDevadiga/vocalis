# Security and privacy

Authenticated APIs require `x-api-key`; only SHA-256 digests of keys are stored. Tenant ID is taken from that digest for every call/document/lead/appointment read. PostgreSQL enforces tenant-consistent parent references for events, CRM jobs, and appointment operations. Browser demo access is limited to a configured tenant and chat only. The Twilio webhook checks `X-Twilio-Signature` against the configured public URL and form parameters before creating a call. Gather turns have durable leases keyed by call and turn, reject conflicting payloads, and atomically save call state with the cached TwiML result. Expired leases can be reclaimed after two minutes. See [Twilio's signature guidance](https://www.twilio.com/docs/usage/webhooks/webhooks-security). Twilio recommends its SDK validator; the pilot currently implements the form signature algorithm directly, and must be validated against live requests before production.

Secrets are supplied through environment variables and must never be committed. The public browser demo has a bounded, process-local IP limiter only; eviction and restarts reset it, so it is not an abuse-control boundary. API keys have no expiry/rotation. SQLite files contain conversation state, lead names/phone numbers, and call events in plaintext; protect the volume and restrict access. Browser demo sessions require explicit consent before a call record is created. Calls and their events/state are pruned at startup and every 24 hours after the configured retention window (`VOCALIS_CALL_RETENTION_DAYS`, default 30 days). This does not delete appointment, lead, or knowledge records; those need separate lifecycle policies. No call recordings are stored. Applicable call processing, notification, marketing, and retention rules vary by jurisdiction and must be reviewed before real use. The retention job is best-effort if the database is unavailable, and a successful backup remains an operator responsibility.

Browser audio messages are capped at 30 seconds based on their declared sample rate, accepted rates are 8–48 kHz, and the Docker Uvicorn command caps WebSocket frames at 5 MB. These bounds limit input before decoding/transcription but do not replace network-level quotas or distributed abuse controls.

WebSocket handshakes with an `Origin` header are accepted only when the origin matches the API origin or an exact entry in `VOCALIS_ALLOWED_ORIGINS` (comma-separated scheme and host origins, such as `https://anvitdevadiga.github.io`). Invalid, `null`, and unlisted origins are rejected before tenant lookup. Non-browser clients without an `Origin` header are still subject to the `/ws` API-key check; `/ws/demo` remains an intentionally public, IP-rate-limited demo when enabled. Origin checks mitigate cross-site WebSocket use but do not replace authentication, host validation, or distributed abuse controls.

`/metrics` is disabled (404) unless `VOCALIS_METRICS_TOKEN` is set and a matching bearer token is provided. It exports only normalized route, method, status, request count, and duration; it does not label metrics with tenant, caller, or call IDs. Keep the token in a secret manager and restrict the metrics route at the reverse proxy to the monitoring system where possible. Counters are process-local and reset on restart.

Retrieved documents are treated as lower-trust context, with a policy instruction and explicit known injection phrases, but there is no reliable prompt-injection guarantee. Do not upload sensitive or untrusted documents without human review. Provider credentials are process-wide but bound to exactly one tenant ID by configuration. Google Calendar can refresh access tokens from a configured OAuth refresh token; HubSpot still uses a static token. For multi-tenant production, use a tenant-scoped secret manager, audit controls, and RBAC. Public demo rate limits and browser cancellation remain process-local. SQLite storage is not suitable for multiple independent replicas; PostgreSQL persistence is supported, but distributed rate limits and shared browser-call coordination still need implementation before scaling the service horizontally.
