# Integrations

## Twilio inbound voice

Create a tenant with `python -m vocalis.admin 'Business' --phone-number +15551234567 --transfer-number +15557654321`. Set `TWILIO_AUTH_TOKEN` and `VOCALIS_PUBLIC_BASE_URL`, then configure that number's voice webhook to `POST <base>/twilio/voice`. The response uses `<Gather input="speech">`; each gather action includes a turn number. The signed delivery is fingerprinted and claimed in the configured database; a repeat gets the cached TwiML, concurrent delivery gets a retryable 503, and a changed payload for the same turn gets 409. Final call state and response are committed atomically. A configured transfer number is dialed for escalation; otherwise an escalation is recorded as requiring follow-up. The integration has not been live-tested with an account in this environment. Twilio's [webhook signature guidance](https://www.twilio.com/docs/usage/webhooks/webhooks-security) describes the exact-URL requirement.

## Google Calendar

The adapter exists, but the hosted demo does not yet have Google Calendar credentials. A dedicated private `Vocalis Portfolio Demo` calendar and a Google Cloud project have been created. The Calendar API is enabled, and an OAuth desktop client has been created with the narrower `calendar.events.owned` scope. The Google OAuth grant still covers events on **all calendars the account owns**; the backend targets only the configured demo calendar. The OAuth app is currently in Testing, where Calendar refresh tokens expire seven days after authorization. Before relying on unattended bookings, publish the OAuth app for personal use, then authorize it and obtain an **offline refresh token**. Google may show an unverified-app warning; do not grant access from anyone else's account. See [Google's audience guidance](https://support.google.com/cloud/answer/15549945) and [personal-use exception](https://support.google.com/cloud/answer/13464323).

Set `GOOGLE_CALENDAR_TENANT_ID`, `GOOGLE_CALENDAR_ID`, `GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET`, and `GOOGLE_CALENDAR_REFRESH_TOKEN` as backend environment variables. The backend exchanges the refresh token for short-lived access tokens and retries once after an unauthorized response. `GOOGLE_CALENDAR_ACCESS_TOKEN` is supported for short local tests but expires and is unsuitable for unattended hosting. Keep every credential out of Git and chat. For the public demo tenant named `Vocalis Portfolio Demo`, the tenant ID is `987d4cc7-da4a-5472-b5ae-8963cb1a36c2`. Public visitors can request bookings, so keep the demo calendar separate from personal and business calendars.

`POST /api/availability` checks a timezone-aware interval against local reservations and, when configured, Google Calendar events. It ignores cancelled and transparent events and follows event-list pagination; provider errors return 503 instead of claiming a slot is free. Booking checks events for a proposed interval, then inserts an event with a deterministic ID derived from the idempotency key. A successful provider response is required before the API says a booking is confirmed. `POST /api/appointments/{id}/reschedule` reserves the local target interval, checks Google Calendar availability excluding the appointment being moved, then updates the event with `If-Match` using its ETag. A private event marker lets retries recover when the update succeeded but the response was lost. Concurrent external calendar users can still take a target slot between availability check and update because Google Calendar does not provide an atomic no-overlap reservation for this workflow. Cancellation deletes the external event before marking the local appointment cancelled; if the response is lost, retry with the same idempotency key. Google treats a missing event as already deleted. The adapter has been tested with provider fakes only, not a live Google account. Business hours, resource calendars, and operator reconciliation remain unfinished. See Google's [OAuth offline access guide](https://developers.google.com/identity/protocols/oauth2/web-server), [event listing](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [event insertion](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [event deletion](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete), [ETag conditional updates](https://developers.google.com/workspace/calendar/api/guides/version-resources), and [event ID constraints](https://developers.google.com/workspace/calendar/api/v3/reference/events).

## HubSpot

Set `HUBSPOT_TENANT_ID` and `HUBSPOT_ACCESS_TOKEN`. POST `/api/leads` with `sync_hubspot: true` and an email to request a HubSpot upsert keyed by email. The lead and a tenant-scoped sync job are committed together locally before calling HubSpot. If the provider call fails, the API returns `202` with `crm_sync: "pending"`; the lead remains saved and the exception type is retained without provider text or contact data. Retry an individual job with `POST /api/leads/{lead_id}/sync`; this call requires the same tenant API key and returns `404` for another tenant's lead. The optional worker can run continuously with `python -m vocalis.crm_worker` or through `docker compose --profile crm-worker up -d`. Each worker process is configured for one HubSpot tenant. Jobs use database leases, stale-claim fencing, bounded concurrency, and exponential backoff. HubSpot upsert is keyed by email so an unknown provider outcome can be retried safely. Phone-only leads remain local. The adapter has not been live-tested and does not yet handle CRM field mapping, OAuth refresh, or conflict reconciliation. See the [HubSpot upsert endpoint](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/objects/batch/upsert-objects).
