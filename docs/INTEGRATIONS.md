# Integrations

## Twilio inbound voice

Create a tenant with `python -m vocalis.admin 'Business' --phone-number +15551234567 --transfer-number +15557654321`. Set `TWILIO_AUTH_TOKEN` and `VOCALIS_PUBLIC_BASE_URL`, then configure that number's voice webhook to `POST <base>/twilio/voice`. The response uses `<Gather input="speech">`; each gather action includes a turn number. The signed delivery is fingerprinted and claimed in the configured database; a repeat gets the cached TwiML, concurrent delivery gets a retryable 503, and a changed payload for the same turn gets 409. Final call state and response are committed atomically. A configured transfer number is dialed for escalation; otherwise an escalation is recorded as requiring follow-up. The integration has not been live-tested with an account in this environment. Twilio's [webhook signature guidance](https://www.twilio.com/docs/usage/webhooks/webhooks-security) describes the exact-URL requirement.

## Google Calendar

The Google Cloud project, Calendar API, OAuth branding, desktop client, and private `Vocalis Portfolio Demo` calendar have been created. The OAuth app is published for personal use and uses the approved `calendar.events.owned` scope. This scope grants the app access to events on all calendars owned by the authorizing account. `GOOGLE_CALENDAR_ID` is the only calendar where Vocalis creates events; `GOOGLE_CALENDAR_BUSY_IDS` controls which calendars block a proposed time. The refresh-token grant has not yet been completed, so the hosted demo must remain fail closed for bookings until credentials are configured. Google may show an unverified-app warning; authorize only the intended Vocalis app from the owner's account. See [Google's audience guidance](https://support.google.com/cloud/answer/15549945) and [personal-use exception](https://support.google.com/cloud/answer/13464323).

Set `GOOGLE_CALENDAR_TENANT_ID`, `GOOGLE_CALENDAR_ID`, `GOOGLE_CALENDAR_BUSY_IDS`, `GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET`, and `GOOGLE_CALENDAR_REFRESH_TOKEN` as backend environment variables. Use `primary,<Vocalis demo calendar ID>` for `GOOGLE_CALENDAR_BUSY_IDS` so personal commitments block slots while new events remain in the demo calendar. Also set `VOCALIS_TIMEZONE=Asia/Kolkata`. The backend exchanges the refresh token for short-lived access tokens and retries once after an unauthorized response. `GOOGLE_CALENDAR_ACCESS_TOKEN` is supported for short local tests but expires and is unsuitable for unattended hosting. Keep every credential out of Git and chat. For the public demo tenant named `Vocalis Portfolio Demo`, the tenant ID is `987d4cc7-da4a-5472-b5ae-8963cb1a36c2`. Public visitors can request bookings, so keep the demo calendar separate from personal and business calendars.

The voice assistant checks local reservations and configured Google calendars before asking the caller to confirm, then checks again before creating the event. `POST /api/availability` requires a timezone-aware interval and checks the same calendars. Cancelled and transparent events do not block a slot; event pagination is followed and provider errors fail closed. The event has a deterministic ID derived from the idempotency key and explicit popup reminders at 24 hours and 2 hours. `POST /api/appointments/{id}/reschedule` reserves the local target interval, checks Google Calendar availability excluding the appointment being moved, then updates the event with `If-Match` using its ETag. A private event marker lets retries recover when the update succeeded but the response was lost. Google Calendar does not offer an atomic no-overlap reservation for this workflow, so an external calendar user could still claim a slot between the final check and insertion. Cancellation deletes the external event before marking the local appointment cancelled; if the response is lost, retry with the same idempotency key. The adapter is tested with provider fakes only, not a live Google account. Working hours and operator reconciliation remain unfinished. See Google's [OAuth offline access guide](https://developers.google.com/identity/protocols/oauth2/web-server), [event listing](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [event insertion](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [event deletion](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete), [ETag conditional updates](https://developers.google.com/workspace/calendar/api/guides/version-resources), and [event ID constraints](https://developers.google.com/workspace/calendar/api/v3/reference/events).

## HubSpot

Set `HUBSPOT_TENANT_ID` and `HUBSPOT_ACCESS_TOKEN`. POST `/api/leads` with `sync_hubspot: true` and an email to request a HubSpot upsert keyed by email. The lead and a tenant-scoped sync job are committed together locally before calling HubSpot. If the provider call fails, the API returns `202` with `crm_sync: "pending"`; the lead remains saved and the exception type is retained without provider text or contact data. Retry an individual job with `POST /api/leads/{lead_id}/sync`; this call requires the same tenant API key and returns `404` for another tenant's lead. The optional worker can run continuously with `python -m vocalis.crm_worker` or through `docker compose --profile crm-worker up -d`. Each worker process is configured for one HubSpot tenant. Jobs use database leases, stale-claim fencing, bounded concurrency, and exponential backoff. HubSpot upsert is keyed by email so an unknown provider outcome can be retried safely. Phone-only leads remain local. The adapter has not been live-tested and does not yet handle CRM field mapping, OAuth refresh, or conflict reconciliation. See the [HubSpot upsert endpoint](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/objects/batch/upsert-objects).
