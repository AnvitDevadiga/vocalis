## GitHub Pages portfolio

`site/index.html` is a standalone static project page. The Pages workflow deploys it from `main` after GitHub Pages is configured to use GitHub Actions. This provides a public resume URL without implying the voice backend is live. The backend remains separate and needs persistent HTTPS/WebSocket hosting.

# Deployment

The default Docker Compose setup starts FastAPI with a persistent SQLite volume for local evaluation. For a hosted multi-replica deployment, provide a PostgreSQL DSN through `VOCALIS_DATABASE_URL` (for example `postgresql+psycopg://user:password@db-host:5432/vocalis`) and run the container. The Docker startup module runs `alembic upgrade head` before starting Uvicorn; set `VOCALIS_AUTO_MIGRATE=0` only when migrations are run as a separate release step. The store refuses to start if the PostgreSQL schema is missing or out of date. Never commit the DSN or provider secrets.

Use `GET /api/health/live` for process liveness and `GET /api/health` for readiness. Readiness checks the configured database and returns HTTP 503 when it cannot be reached; it reports provider configuration separately because providers are not required for basic service startup. The container health check uses readiness so an unavailable database is visible to the platform.

HTTP request counts and latency histograms are available at `/metrics` only when `VOCALIS_METRICS_TOKEN` is configured; scrape with `Authorization: Bearer <token>` and keep the endpoint private. Counters are per-process and reset on restart. Add external alerts for readiness failures, 5xx growth, and latency changes. No monitoring or alert destination is provisioned by this repository.

### Free portfolio preview

The repository includes a Render Blueprint at `render.yaml`. Render is the recommended backend host because this app is a Dockerized FastAPI service with long-lived WebSockets. Vercel is a good home for the static portfolio, but its serverless limits and evolving WebSocket support make it a less direct fit for this existing service. Create a Render Blueprint from this repository and supply `VOCALIS_DATABASE_URL` from a PostgreSQL provider plus your existing `GROQ_API_KEY` as a secret. Neon documents a free tier with 1 GB per project and a monthly compute allowance; keep a separate verified backup because free-service limits can change. Render's free web service sleeps after 15 minutes without inbound traffic, takes about a minute to restart, and has an ephemeral filesystem. Render's free Postgres expires after 30 days, so use an external free database such as Neon for a continuing preview. This setup is for portfolio traffic, not a production service. See the [Render free-instance limits](https://render.com/docs/free), [Render WebSocket support](https://render.com/docs/websocket), [Vercel limits](https://vercel.com/docs/limits), and [Neon free-plan limits](https://neon.com/blog/neon-free-plan-1-gb-per-project).

The Blueprint enables the demo only when both the database and `GROQ_API_KEY` are configured. On startup, it creates one stable tenant named `Vocalis Portfolio Demo` with a random discarded API key; the public socket is restricted to this tenant and rate-limited. If you prefer manual provisioning, use `python -m vocalis.provision_demo_tenant` after migrations. Set `VOCALIS_ALLOWED_ORIGINS` to the exact frontend origin (`https://anvitdevadiga.github.io`). To verify the deployed service before changing the portfolio, open `https://anvitdevadiga.github.io/vocalis/?backend=https%3A%2F%2FYOUR-SERVICE.onrender.com`; replace `YOUR-SERVICE` with the assigned Render host. Once verified, set `window.VOCALIS_BACKEND_URL` in `site/config.js` to that HTTPS origin and push; GitHub Pages will deploy the demo link. The demo page connects by WebSocket to the API host itself. GitHub Pages cannot host the API or maintain its WebSockets.

### Retention and database backups

`VOCALIS_CALL_RETENTION_DAYS` defaults to 30. At service startup and every 24 hours, the API deletes ended calls (and stale active calls) older than this window, including their event rows and stored conversation state. Run `python -m vocalis.maintenance` for a dry-run count; `python -m vocalis.maintenance --apply` performs the deletion. This policy covers call records only; appointments, leads, and knowledge documents are retained separately and need owner-approved lifecycles. A failed cleanup is logged without caller content and retried on the next cycle.

Create a new, private backup with `python -m vocalis.backup --output /secure/backups/vocalis-YYYYMMDD.dump`. SQLite uses the online backup API, verifies integrity/foreign keys, and creates a mode-0600 file. PostgreSQL requires `pg_dump` and `pg_restore` on the operator machine; it creates a custom-format archive, verifies that archive, uses libpq environment variables instead of putting the DSN on the process command line, and refuses to overwrite a backup. Store backups outside the app host and restrict access because they contain PII. For PostgreSQL recovery, restore into a newly created empty test database with `pg_restore --no-owner --no-privileges --dbname "$RESTORE_TEST_DATABASE_URL" /secure/backups/vocalis-YYYYMMDD.dump`, then start the app against that database and verify tenant, call, appointment, and lead counts before planning any production restore. Do not run a restore over the live database as a test.

PostgreSQL migrations live in `alembic/versions`. They create the tenant-scoped tables, foreign keys, and partial unique indexes used for active appointment slots and pending appointment operations. Multi-step appointment, webhook-turn, and CRM transactions take PostgreSQL transaction-level advisory locks scoped to the tenant; webhook-event deduplication also uses a unique key, and pending CRM worker claims use `FOR UPDATE SKIP LOCKED`. The CI workflow starts PostgreSQL and runs migration-backed integration tests, including concurrent booking checks.

To transfer the current SQLite store, first stop the API and CRM worker, configure `VOCALIS_DATABASE_URL` for an empty PostgreSQL database, and run `python -m alembic upgrade head`. Then run `python -m vocalis.migrate_sqlite --source data/vocalis.db --backup data/vocalis.pre-postgres.sqlite`. The tool creates a consistent SQLite backup through SQLite's online backup API, with file permissions restricted to the current user. It then opens SQLite read-only, checks integrity and foreign keys, validates every expected table and column, and copies in one PostgreSQL transaction while preserving IDs, idempotency records, webhook leases, and pending appointment/CRM work. It resets the event ID sequence and verifies row counts before commit. It refuses an existing backup filename, unknown source tables, stale schemas, or any non-empty PostgreSQL target. Keep the old API and worker stopped until you have verified the reported counts and started the application against PostgreSQL; writes made to SQLite after the snapshot are not included.

To serve remote microphone users, put FastAPI behind public HTTPS with WebSocket proxying. Twilio requires a publicly reachable HTTPS endpoint and exact `VOCALIS_PUBLIC_BASE_URL`; the phone number must POST to `/twilio/voice`. Set `TWILIO_AUTH_TOKEN`, create a tenant configured with the matching `To` number, and configure provider keys. Place real provider test calls before exposing the number to customers.

If the browser page and API use different origins, set `VOCALIS_ALLOWED_ORIGINS` to a comma-separated list of exact origins, such as `https://anvitdevadiga.github.io` (no path or trailing slash). Same-origin browser connections work without this setting. The WebSocket service rejects unlisted browser origins before looking up a tenant.

The optional HubSpot worker shares the configured database with the API. Configure `HUBSPOT_TENANT_ID` and `HUBSPOT_ACCESS_TOKEN`, then start it with `VOCALIS_ENV_FILE=.env docker compose --profile crm-worker up -d` or run `python -m vocalis.crm_worker` beside the API. It requires the same database URL or path. Each worker process is configured for one HubSpot tenant.

This deployment is **not production hardened**. Distributed rate limiting, shared browser-call coordination, provider readiness checks, metrics export, alerting, secret rotation, automated off-host backup scheduling, restore drills, retention for non-call records, and privacy review remain. SQLite mode requires one API replica. On a real deployment, configure strict origin/host controls, TLS, managed database backups, network egress policy, and provider retry/error monitoring. GitHub Pages hosts only the static project page and cannot maintain these WebSockets.
